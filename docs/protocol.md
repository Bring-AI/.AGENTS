# 目录协议 v1

## 路径与职责

| 路径 | 用途 | 加载时机 |
| --- | --- | --- |
| `AGENTS.md` | 项目背景、公共规则及角色路由 | 开始任务 |
| `.AGENTS/<role>/AGENTS.md` | 角色目标、职责边界、交接对象 | 选择或切换角色 |
| `.AGENTS/<role>/memory/MEMORY.md` | 当前事实、决策、经验和未解决问题 | 选择或切换角色 |
| `.AGENTS/<role>/skills/<skill>/SKILL.md` | 可复用方法与适用条件 | 技能匹配时 |
| `.AGENTS/<role>/local/` | 不提交的临时工作资料 | 当前实例自行管理 |

角色和技能名为 1–63 个小写字母、数字、连字符，首尾为字母或数字；排除 Windows 保留设备名（如 `con`、`nul`、`com1`）。大小写固定，便于跨平台协作。

## Memory：知道什么

`memory/MEMORY.md` 直接保存当前事实、决策和经验，不是完整会话日志。每项知识使用一个小节；通过 Git 历史追溯修改。并发任务使用独立 worktree，在评审时协调同一文件的修改。每个小节建议包含：

```markdown
## 决策或经验标题

- Date: YYYY-MM-DD
- Owner: developer / task-142
- Status: active
- Scope: 适用模块或条件
- Evidence: 提交哈希、代码路径、测试结果或可访问的来源
- Review after: 相关接口变更时，或 YYYY-MM-DD

### Finding
已确认的事实；将假设与结论明确区分。

### Consequence
今后什么情况下该使用这一信息。
```

状态建议使用 `active`、`superseded`、`archived`。新结论取代旧结论时，注明替代关系并更新内容，保留 Git 追溯线索。遇到与当前代码冲突的记忆先核验，确认后修正。从当前文件移除长期无用的内容，历史通过 Git 保留，不要让记忆无限增长。日期、证据和状态是维护约定，需要维护者核验其真实性。

## Skill：怎么做

技能由一个目录和 `SKILL.md` 组成。文件使用 YAML frontmatter，至少包含 `name` 和 `description`；名称与目录一致。描述应表达具体能力和使用条件，正文给出必要流程与验证方式。

```markdown
---
name: api-change
description: 修改 API 契约时核查调用方、兼容性和迁移验证。
---

# API change

确认接口使用方与现有契约，再确定兼容策略。针对受影响调用路径验证变更，记录需要的迁移步骤。
```

需要时添加 `scripts/`、`references/`、`assets/`，从正文链接到具体资源；不要默认将它们全部加入上下文。由 agent 按任务需要读取适用技能及其引用的资源。

技能格式和加载方式以使用的客户端为准。本仓库中的技能文件是可复制和修改的示例。

## 加载和优先级

先读根 `AGENTS.md` 中的项目背景和公共约定，再读角色职责和记忆，再按任务选技能。加载顺序用于节省上下文，不建立新的指令优先级。客户端原生规则和用户任务始终按其原有机制生效。角色约定不能授权任务之外的操作，历史记录不能覆盖现行规则。

在项目入口中明确列出这三个文件的路径，让 agent 显式读取。角色记忆保存在 `memory/MEMORY.md`，技能正文按任务需要读取。目录约定本身不会自动加载文件或限制访问范围。

## 多 agent 协作

- 用角色划分长期知识，用任务标识区分运行实例，不把进程名当作角色名。
- 两个 developer 并行时，各自使用独立 worktree 或明确的文件分工；合并时核对 `memory/MEMORY.md` 的并发修改。
- 交接说明完成内容、证据、剩余问题和涉及文件。接收角色核验后更新自己的摘要。
- 共同的项目背景先协调再写入根 `AGENTS.md`；不要在每个角色目录复制同一份事实。
- Git 合并解决文本冲突，评审解决语义冲突。本协议没有锁或自动仲裁器。

## 从单一 AGENTS.md 迁移

1. 保留公共规则、命令和路径范围约定。
2. 将职责说明移入相应 `AGENTS.md`。
3. 将重复工作方法提炼为技能；历史结论提炼成带证据的记忆。
4. 在原入口合并角色读取说明，核对引用路径与实际文件一致。
5. 用一次实际任务验证客户端确实读取了所选角色文件。
