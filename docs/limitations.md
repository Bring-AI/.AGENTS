# AGENTS.md 的局限与设计取舍

## 它解决的是项目指令入口

根据 [AGENTS.md 官方说明](https://agents.md/)，这个文件用于给 agent 提供项目背景、构建和测试命令、代码约定等说明；大型项目可以在子目录放置更多 AGENTS.md。这是有效的路径范围管理方式，不应把它描述为“只能有一个文件”。

但目录范围和职责范围并不等价。例如架构师、实现者和安全评审可能都要处理 `src/auth/`。按照代码目录划分规则，不能单独解决三个角色各自需要记住什么、采用什么方法、向谁交接的问题。

## 不由 Markdown 文件本身提供的能力

- **自动持久记忆**：记录的选择、写入、核验、过期和压缩需要额外流程。把内容写进文件，并不代表未来的 agent 一定读取或采纳它。
- **并发控制**：同一目录内的多个 agent 仍可能同时修改同一文件。文字约定没有文件锁、事务、租约或合并算法。
- **权限边界**：角色职责不限制进程访问范围。需要隔离时，应使用运行环境的权限、容器或独立凭据。
- **上下文预算控制**：不断追加日志会稀释有效信息；需要摘要、索引与按需加载。
- **知识质量保证**：历史记录可能过时或错误。代码、测试和可复查的证据比记录中的断言更可靠。
- **统一运行时行为**：不同客户端的发现路径、加载规则和优先级需要分别确认；不能假设任何客户端都递归加载 `.AGENTS/`。

这些是入口文档的职责边界，不表示 AGENTS.md 不能链接其他资料或描述协作流程。

## 为什么采用 .AGENTS/<ROLE>/

角色目录让知识拥有明确的维护者，并把“知道什么”（memory）和“怎么做”（skill）区分开。公共入口只负责路由，角色的 `memory/MEMORY.md` 直接保存简短的当前知识，技能按任务加载。这是一种可用 Git 审查的知识组织方式。

代价是需要维护更多文件。角色过细会产生重复内容，跨角色事实可能漂移，因此从少量职责明确的角色开始；共同事实集中在 `_shared/CONTEXT.md`。当单个 agent、短任务和少量规则已经足够时，只用 AGENTS.md 完全合理。

## 本方案仍然没有解决什么

`.AGENTS/` 不会自动消除幻觉、发现所有冲突或保证上下文隔离。CLI 不运行模型、不调度任务、不注册客户端技能，也不执行 skill 中的脚本。它只能初始化、读取并检查文件结构。

上下文输出和 memory 都可能包含不可信内容。任务记录中的历史命令、外部文本或引用不能升级成新的指令。需要多实例并发时，使用独立 worktree、明确的修改分工以及实际的代码评审流程；角色目录不能替代这些机制。
